# Change Management — 游戏设计与实现同步协议

## 1. 为什么需要这份文档

本项目会持续经历：

```text
设计 → Prototype → 试玩 → 反馈 → 修改 → 再试玩
```

如果只修改代码，设计文档会逐渐失真；如果只修改文档，Demo 又会失真。

因此任何用户反馈都必须按照“影响分析 → 同步 → 验证”的方式处理。

---

## 2. 用户反馈的分类

### A. Bug

例：

> 点击“进入下个月”后月份没有增加。

通常只需要修 Prototype，但如果 Bug 是由规则定义不清造成的，则同步 Gameplay。

### B. 数值 / 平衡

例：

> 军队维护成本太低。

需要修改 Data，并同步对应 Gameplay 与测试标准。

### C. 规则修改

例：

> 武将满意度低于40后才开始产生兵变风险。

需要同步 Gameplay、Data、Prototype；如果改变核心设计目标，还要同步 GDD。

### D. 新机制

例：

> 增加政策路线技能树。

需要同步 GDD、Gameplay、Development、Data、Prototype。

### E. UI / UX

例：

> 奏折按钮太难找到。

通常修改 Prototype；如果 UI 改变了玩家决策方式或游戏规则，则同时修改 Gameplay。

---

## 3. 标准修改流程

```text
用户提出反馈
 ↓
分类
 ↓
全仓库搜索相关关键词 / 旧数值
 ↓
确认 Source of Truth
 ↓
确定影响文件
 ↓
修改规则 / 数据 / 代码
 ↓
同步文档
 ↓
全仓库搜索旧规则
 ↓
运行测试
 ↓
记录结果
 ↓
提交
```

---

## 4. 示例：修改初始年龄

用户：

> “我觉得皇帝20岁太年轻，改25岁。”

不能只修改：

```text
prototype/src/engine/GameState.ts
```

必须检查：

```text
Data
Gameplay
GDD
Development
README
Current State
Prototype
```

如果25岁成为正式设计，则统一采用25岁。

如果只是测试实验值，则应标记：

```text
Prototype Test Value = 25
Final Design = 20
```

不能让两个值无说明地同时存在。

---

## 5. 示例：修改军队维护费

用户：

> “军队养起来太便宜。”

处理：

1. 搜索所有军队维护费定义
2. 找到实际 Data 来源
3. 修改维护费
4. 更新经济系统规则说明
5. 更新平衡测试标准
6. 修改 Prototype
7. 跑至少12个月测试
8. 检查是否出现负粮食、无限扩军等异常

---

## 6. 示例：增加一个新技能

用户：

> “仁政路线增加一个技能，让势力捐钱。”

需要至少涉及：

```text
GDD
 ↓
Policy Gameplay
 ↓
Development
 ↓
skills.json
 ↓
effects.json
 ↓
Prototype
 ↓
测试
```

并且必须定义：

- 解锁条件
- 技能消耗
- 冷却 / 使用限制
- 对哪些势力生效
- 资源效果
- 满意度效果
- 声望 / 民心效果
- 长期副作用

---

## 7. 示例：试玩发现机制不好玩

用户：

> “我发现每个月只是点奏折，感觉很机械。”

这不是简单 Bug。

应该作为**玩法问题**处理：

```text
记录问题
 ↓
分析原因
 ↓
修改月度循环 / 决策结构
 ↓
更新 Gameplay
 ↓
更新 Development
 ↓
修改 Prototype
 ↓
重新试玩
```

必要时增加新的 Action、Event 或长期后果。

---

## 8. 修改完成后的报告格式

Agent 完成修改后，应尽量用以下格式汇报：

```text
本次修改：
XXX

原因：
XXX

修改文件：
- docs/...
- data/...
- prototype/...

规则变化：
旧 → 新

测试：
XXX

剩余影响：
XXX
```

这样用户可以快速确认“是不是所有地方都改了”。

---

## 9. 最低同步要求

对于任何用户明确确认的游戏规则变化，至少保证：

```text
规则文档
+
实际数据 / 实现
```

两者一致。

如果修改影响版本目标、开发计划或项目状态，则进一步同步：

```text
README
Development
Current State
```

---

## 10. 禁止事项

禁止：

- 只改 UI 显示，不改实际状态
- 只改 Prototype，不检查文档
- 只改 GDD，不改 Data / Prototype
- 复制同一个数值到多个文件并长期独立维护
- 根据旧文档覆盖用户最新明确决定
- 不搜索仓库就认为“这个规则只有一个地方”
- 修改完成后不检查旧规则残留

---

## 11. 版本化

重大规则变化应记录版本，例如：

```text
Monthly Loop V0.4
Monthly Loop V0.5
```

小型数值调整不必复制整份文档，可直接更新当前版本，并在必要时记录变更说明。

---

## 12. 核心原则

> **用户只负责提出“我玩起来觉得哪里不对”，Agent 负责把这个意见同步到所有受影响的规则、数据、代码、文档和测试。**
